## F1

Severity: BLOCKING
Status: defect
Claim: Restoring an earlier `.gitignore` can permanently delete ignored content while reporting a successful rollback.
Where: `design/10-design.md:624`–`633`, Data model — Checkpoint; the restore sequence and ignored-path invariant in `design/20-contract.md:1394`–`1426`; brief DoD #6 and its exclusion at `design/00-brief.md:43`–`50`. The implemented sequence is also present at `src/agent-console/extensions/checkpoints/index.ts:263`–`314`.
Breaks when: Target checkpoint A contains a `.gitignore` without `local-data/`. A later turn adds that ignore rule and creates `local-data/operator.txt`. Restoring A first makes safety checkpoint B with `add -A`, which excludes the file. `read-tree --reset -u A` then restores the old `.gitignore`, making the file unignored, and `clean -fd` deletes `local-data/`. The operation is sequential and needs no concurrent writer or filesystem failure.
Consequence: The operator loses content that the brief promises a restore never removes. Neither A nor B contains its bytes, so the safety checkpoint cannot undo the loss. Both prescribed success checks pass. The target's ignored manifest and the post-clean ignored listing can both be empty, so the final report can also omit the deleted path. The design's assertion that the capture and removal sets are identical is false when the restore changes the ignore rules those commands consult.
Cost: Cheap to address now because the checkpoint boundary contains the mechanism; expensive after an affected restore because excluded bytes have no recovery source in the checkpoint history. The existing implementation means this is already an operational exposure, not only a future migration concern.

Recommended classification: **defect**. D31 and D112 retain the symmetry argument, and D182 accepts leaving ignored content untouched with an approximate metadata report. None accepts deleting content excluded from the safety checkpoint. The new evidence is a restore changing its own exclusion rules and silently deleting that content; the mechanism contradicts the higher-precedence brief rather than exposing a missing brief decision.

Evidence: Reproduced in an isolated temporary workspace with a separate shadow Git directory on Windows using `git version 2.55.0.windows.5`. Before restore, `ls-files --others --ignored --exclude-standard` named `local-data/operator.txt`; B's recursive tree listing contained only `.gitignore`. After `read-tree --reset -u A` the payload still existed. `clean -fd` printed `Removing local-data/`, after which the payload was absent. `diff --quiet A` exited 0 and `ls-files --others --exclude-standard` returned no paths. This reproduces the Git sequence; the console API and Linux execution were not exercised.

Reproduction, in a disposable workspace with `GIT_DIR` pointing to a separate initialized shadow repository and a configured commit identity:

```text
1. Write .gitignore containing only a comment; git add -A; git commit -m target; record A.
2. Replace .gitignore with local-data/; create local-data/operator.txt with synthetic bytes.
3. git add -A; git commit -m safety; record B.
4. git ls-files --others --ignored --exclude-standard
5. git ls-tree -r --name-only B
6. git read-tree --reset -u A
7. git clean -fd
8. git diff --quiet A
9. git ls-files --others --exclude-standard
```
